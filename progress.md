## 1. Vision (the one-paragraph pitch)

EyeSight can't be commanded on gas/brake over CAN on the pre-global platform — that's settled (see §7). So instead of *replacing* longitudinal control, **ride it**: let the comma's vision model decide the right speed (for lead cars EyeSight loses lock on, and for curves/limit changes), then have openpilot **spoof the steering-wheel ACC buttons** to move EyeSight's *own* setpoint down/up. EyeSight does the actual braking; we just turn its dial. "Poor man's" longitudinal because it inherits EyeSight's floor (~25 mph, can slow but not stop) and EyeSight's decel rate — but it removes the constant manual intervention.

**Guiding principle:** validate the *decision* before automating the *actuation*. Phase 1 puts a human thumb in the loop as the actuator so the speed-target logic can be proven with zero risk to the car.

## 2. Key facts / constraints (RAG anchors — stable truths)

- Pre-global exposes **no** openpilot gas/brake actuation. Direct CAN longitudinal is undecoded and unattempted community-wide (Aug 2023 bounty still unclaimed as of last check).
- Lateral works only via the community Subaru branch; steering is **torque-based** with a max-torque cap.
- EyeSight stock ACC **minimum set speed ≈ 25 mph** (CONFIRM exact value on car). Below that, EyeSight ACC drops out → **driver must brake for anything requiring < ~25 mph**. This bounds the whole feature: *it slows the car, it does not stop the car.*
- Decel aggressiveness after a setpoint change is **EyeSight's, not tunable by us**. We only control *when* and *by how much* the setpoint moves, and the *cadence* of injected button events.
- OSM map data is served on-device by the **`mapd`** daemon (pfeiferj lineage). Region download enables map-based speed-limit + curve features. Full continental US dataset confirmed on-device, 5.4 GB, current as of last check.
- sunnypilot already ships the two relevant features on long-enabled cars:
  - **MTSC** (Map Turn Speed Control, "SCC-M") — target speed from **OSM curvature**, looks *ahead beyond sensor range* → primary source for advance warning.
  - **VTSC** (Vision Turn Speed Control, "SCC-V") — target speed from the **model's predicted path curvature**; a `VisionTurnController` estimates lateral accel and computes `v_turn`. Near-field only (sees what's currently ahead) → good cross-check, no map dependency.
- **Confirmed via source (2026-07-20):** `plannerd`'s SmartCruiseControlMap/Vision computation runs **unconditionally**, gated only on `carControl.enabled` (system engaged) — not on `CP.openpilotLongitudinalControl`. This is why Phase 1 is possible at all on a lateral-only car: the speed-target math genuinely runs live regardless of actuation capability.
- **Confirmed via source (2026-07-20):** sunnypilot's `ui_state.py` `_enforce_constraints()` force-deletes `SmartCruiseControlMap`/`SmartCruiseControlVision` params on any car lacking both long control and ICBM — a *product-level* UI gate, unrelated to what the underlying computation actually needs. Patched in our fork (see Phase 1 below) since it doesn't apply to a read-only advisory use case.
- **Confirmed via sunnypilot founder, community forum, 2026-07-20:** ICBM (Intelligent Cruise Button Management — sunnypilot's own button-spoofing feature, exactly our Phase 3 idea) is **unimplemented for all Subaru platforms**, not just ours. Quote: *"The necessary button message structure and routing aren't exposed or implemented by Subaru in a way that supports emulation yet... this isn't something we're actively pursuing... would likely need to be a community-driven effort."* Also mentioned: *"previous POCs using actuation test commands via UDS in diagnostic sessions, but those were never explored further"* — a genuinely new avenue for Phase 2 (see below). Source: https://community.sunnypilot.ai/t/enabling-icbm-on-17-impreza/191

## 3. The physics we're reusing (so the doc is self-contained)

Safe/comfortable curve speed is set by **target lateral acceleration**, *not* steering torque (common confusion — torque is actuator authority, a separate ceiling):

```
v_max = sqrt(a_lat_target / κ)          κ = curvature = 1/R
```

- Comfort target `a_lat_target` ≈ **1.8–2.5 m/s²** (what MTSC/VTSC use; tune to taste).
- Curvature κ comes from OSM way geometry (MTSC) or the vision path (VTSC).
- Torque cap matters *separately*: if a curve needs more steering torque than the community branch is allowed to command, lateral control runs wide regardless of speed. Worth logging as a distinct failure mode, but it does **not** drive the speed number.

## 4. Architecture (tandem model)

```
[mapd / OSM curvature]  ─┐
                         ├─► speed-target calc (reuse MTSC/VTSC math)
[vision model path]     ─┘         │
                                   ▼
                    target_v + distance_to_event
                                   │
        Phase 1 ───────────────────┼─────────────── Phase 2/3
        emit ADVISORY                       emit BUTTON-SPOOF cmd
   (alert text + audio: "curve,          (injected ACC set-/res+ frames
    reduce to 35 in 400 ft")              → EyeSight moves its setpoint)
                                   │
                                   ▼
                          EyeSight does the braking
```

## 6. Difficulty read — building the UI

The honest version:

- **Custom on-screen HUD widget from scratch:** *moderate–hard right now*, because openpilot's UI is mid-migration Qt/C++ → raylib/Python. Building a bespoke widget means building on a moving target.
- **Advisory via the existing alert/event system:** *easy–moderate*, and it's the right MVP — confirmed correct in practice. Emit an event with the computed target speed + distance; the alert text + chime already render on whatever UI stack is live. Pure Python in the controls/planner layer, no C++, no rendering code. Phase 1 shipped with **zero new widget files** — the whole implementation was event/text wiring into infrastructure already composed on-screen.

Net: the *speed-target math* was largely done already (MTSC/VTSC exist and run regardless of long control). The real Phase-1 work ended up being: plumbing their output to an advisory, working around a product-level settings gate that assumed every car either has long control or ICBM, and tuning trigger thresholds (min speed, once-per-curve debounce). All tractable. The hard, risky novelty is still all in Phase 2/3.

## 11. 🟢 Incident (opened 2026-07-21, fix deployed 2026-07-21, confirmed resolved via real driving)

**Symptom:** On the first real validation drive of `phase1-curve-advisory` (commit `fa6604a`), cruise control was completely unavailable from the start of the drive — repeated attempts to engage both openpilot-assisted cruise and stock/"natural" cruise threw the same persistent error. Car remained driveable manually the whole time (no physical danger, just no ACC). User observed `plannerd` was not running.

**Leading hypothesis (strong circumstantial evidence, not yet confirmed via live traceback):** stale generated capnp C++ bindings. `cereal/custom.capnp` is the schema *source*, but openpilot also ships pre-generated bindings compiled from it (`cereal/gen/cpp/custom.capnp.h` / `.c++`), which require an explicit `scons` build to regenerate — a plain `git pull`/`git checkout` + reboot does **not** rebuild them. Checked both generated files in the local dev clone directly: neither contains the `distance` field or `curveSpeedAdvisory` enum value added on this branch — they're stale relative to the schema source, and nothing (locally or, going by symptoms, possibly on-device) ever regenerated them. `longitudinal_planner.py` unconditionally writes `sccMap.distance = ...` on every single publish call, starting from the first frame — if the compiled schema plannerd actually runs against lacks that field, this throws immediately, matching "immediately... not running" exactly, and a crash-looping `plannerd` plausibly explains losing cruise access entirely (it feeds the core control state machine, not just the advisory).

**Not yet confirmed:** whether comma's manager auto-runs an incremental `scons` build on every boot (if it does, the above theory needs revisiting — the crash could be something else, or the auto-build could itself be failing silently and that failure is the real thing to chase).

**Real process gap this exposed:** earlier "you're clear to test" verification only checked that `SmartCruiseControlMap`/`CurveSpeedAdvisory` params persisted in the params store — never checked that `plannerd` was actually alive and publishing without crashing. Params persisting says nothing about process health. **Do not repeat this gap** — any future redeploy must confirm the actual process is running clean (e.g. `pgrep -af plannerd`, check for crash-loop in logs, tail `plannerd`'s recent log output) before calling it safe to drive on, not just that a param file has the right value in it.

```

extension common/params_pyx.so (which enforces a strict key allowlist) was never
rebuilt, so Params.get_bool("CurveSpeedAdvisory") raises
common.params_pyx.UnknownKeyName on the very first call, in
CurveAdvisoryHelper.__init__, crashing plannerd's constructor on every single

```
**Deeper structural finding:** this device's branch (`phase1-curve-advisory`, forked from `release-mici`) is a true **prebuilt-only release export** — confirmed no `SConstruct` exists anywhere in the tree, on this branch or on `release-mici` itself, and (checked directly against sunnypilot's GitHub) on *any* mici-targeting branch they ship. Only upstream `master` has a buildable tree, and running raw `master` on a daily driver is explicitly discouraged by the community (unreleased, breaking changes). So **on-device `scons` rebuild is not a viable fix, ever, on this branch lineage** — not a one-time miss, a permanent constraint of shipping on a release/prebuilt branch. The `/data/openpilot/prebuilt` marker file that skips the build step in `launch_chffrplus.sh` is itself git-tracked, shipped by sunnypilot's own release commit — not something we broke.
**Fix actually shipped (2026-07-21, commit `70051d5`):** rather than eat a full reinstall (confirmed via community chat logs: re-running `install.sunnypilot.ai/...` for any branch is a full wipe, same calibration/torque-relearn cost as any other fork/install switch — not a lighter incremental patch), `curve_advisory_helper.py`'s two `get_bool("CurveSpeedAdvisory")` call sites now wrap in `try/except UnknownKeyName`, defaulting to `True`. **2026-07-23, later — Phase 1.5 shipped, EyeSight-isolation researched and closed, camera-bus injection tested and closed with a real physical incident.** Lead-vehicle closing-speed advisory (`LeadClosingAdvisory`, on by default) and an opt-in Phase-3-validation guidance tool (`LeadClosingTestGuidance`, off by default) both built, deployed (commit `7d20543`), and confirmed healthy on-device — see §8 decisions log for the design/telemetry-validation writeup. Separately investigated whether physically isolating EyeSight (à la the 2021 "Giraffe" DIY board) could sidestep Q9's bus-contention problem: confirmed via the actual hardware author's own words that preglobal's harness has no controllable relay at all ("I just don't have a relay to worry about and run direct") — that architecture is global-platform-only, closing this avenue the same way Q9 did. Then tested camera-bus injection directly (reasoning: the stop-and-go Throttle/Brake spoof works on bus 2 without contention, so maybe CruiseControl would too): sent one unmodified copy of a real `CruiseControl` frame onto bus 2. **CAN-level error counters stayed completely flat — but the car's dash showed a real "EyeSight Off" fault immediately after, cleared only by a full ignition cycle.** The in-the-moment verdict ("no visible collision") was wrong and got corrected live once the user reported the physical symptom — the CAN-error-counter check was blind to a real vehicle-level consequence one layer up. Root cause, best understanding: the copied frame's rolling counter/checksum was already stale by the time it was sent (real message had moved on), and something upstream of the CAN layer — almost certainly EyeSight itself — treated the mismatch as anomalous and faulted itself off protectively, rather than passively accepting it. **This closes the camera-bus route as decisively as Q9's UDS approach** — a sustained injection (which real button-spoofing needs) would mean continuously re-triggering this same fault for as long as it ran, a worse failure mode than the main-bus collision problem it was meant to avoid. **Lesson for this project going forward: CAN-level health checks (error counters, bus-off state) are necessary but not sufficient — a vehicle-level symptom check (dash, actual system availability) is required too, the same category of gap as the plannerd/process-health lesson, just one layer higher up the stack.**
