## 1. Vision (the one-paragraph pitch)

EyeSight can't be commanded on gas/brake over CAN on the pre-global platform — that's settled (see §7). So instead of *replacing* longitudinal control, **ride it**: let the comma's vision model decide the right speed (for lead cars EyeSight loses lock on, and for curves/limit changes), then have openpilot **spoof the steering-wheel ACC buttons** to move EyeSight's *own* setpoint down/up. EyeSight does the actual braking; we just turn its dial. "Poor man's" longitudinal because it inherits EyeSight's floor (~25 mph, can slow but not stop) and EyeSight's decel rate — but it removes the constant manual intervention.

**Guiding principle:** validate the *decision* before automating the *actuation*. Phase 1 puts a human thumb in the loop as the actuator so the speed-target logic can be proven with zero risk to the car.

## 2. Key facts / constraints (RAG anchors — stable truths)

- Pre-global exposes **no** openpilot gas/brake actuation. Direct CAN longitudinal is undecoded and unattempted community-wide (Aug 2023 bounty still unclaimed as of last check).
- Lateral works only via the community Subaru branch; steering is **torque-based** with a max-torque cap.
- EyeSight stock ACC **minimum set speed ≈ 25 mph** (CONFIRM exact value on car). Below that, EyeSight ACC drops out → **driver must brake for anything requiring < ~25 mph**. This bounds the whole feature: *it slows the car, it does not stop the car.*
- Decel aggressiveness after a setpoint change is **EyeSight's, not tunable by us**. We only control *when* and *by how much* the setpoint moves, and the *cadence* of injected button events.
- OSM map data is served on-device by the **`mapd`** daemon (pfeiferj lineage). Region download enables map-based speed-limit + curve features. Full continental US dataset confirmed on-device, 5.4 GB, current as of last check.
- sunnypilot already ships the two relevant features on long-enabled cars:
  - **MTSC** (Map Turn Speed Control, "SCC-M") — target speed from **OSM curvature**, looks *ahead beyond sensor range* → primary source for advance warning.
  - **VTSC** (Vision Turn Speed Control, "SCC-V") — target speed from the **model's predicted path curvature**; a `VisionTurnController` estimates lateral accel and computes `v_turn`. Near-field only (sees what's currently ahead) → good cross-check, no map dependency.
- **Confirmed via source (2026-07-20):** `plannerd`'s SmartCruiseControlMap/Vision computation runs **unconditionally**, gated only on `carControl.enabled` (system engaged) — not on `CP.openpilotLongitudinalControl`. This is why Phase 1 is possible at all on a lateral-only car: the speed-target math genuinely runs live regardless of actuation capability.
- **Confirmed via source (2026-07-20):** sunnypilot's `ui_state.py` `_enforce_constraints()` force-deletes `SmartCruiseControlMap`/`SmartCruiseControlVision` params on any car lacking both long control and ICBM — a *product-level* UI gate, unrelated to what the underlying computation actually needs. Patched in our fork (see Phase 1 below) since it doesn't apply to a read-only advisory use case.
- **Confirmed via sunnypilot founder, community forum, 2026-07-20:** ICBM (Intelligent Cruise Button Management — sunnypilot's own button-spoofing feature, exactly our Phase 3 idea) is **unimplemented for all Subaru platforms**, not just ours. Quote: *"The necessary button message structure and routing aren't exposed or implemented by Subaru in a way that supports emulation yet... this isn't something we're actively pursuing... would likely need to be a community-driven effort."* Also mentioned: *"previous POCs using actuation test commands via UDS in diagnostic sessions, but those were never explored further"* — a genuinely new avenue for Phase 2 (see below). Source: https://community.sunnypilot.ai/t/enabling-icbm-on-17-impreza/191

## 3. The physics we're reusing (so the doc is self-contained)

Safe/comfortable curve speed is set by **target lateral acceleration**, *not* steering torque (common confusion — torque is actuator authority, a separate ceiling):

```
v_max = sqrt(a_lat_target / κ)          κ = curvature = 1/R
```

- Comfort target `a_lat_target` ≈ **1.8–2.5 m/s²** (what MTSC/VTSC use; tune to taste).
- Curvature κ comes from OSM way geometry (MTSC) or the vision path (VTSC).
- Torque cap matters *separately*: if a curve needs more steering torque than the community branch is allowed to command, lateral control runs wide regardless of speed. Worth logging as a distinct failure mode, but it does **not** drive the speed number.

## 4. Architecture (tandem model)

```
[mapd / OSM curvature]  ─┐
                         ├─► speed-target calc (reuse MTSC/VTSC math)
[vision model path]     ─┘         │
                                   ▼
                    target_v + distance_to_event
                                   │
        Phase 1 ───────────────────┼─────────────── Phase 2/3
        emit ADVISORY                       emit BUTTON-SPOOF cmd
   (alert text + audio: "curve,          (injected ACC set-/res+ frames
    reduce to 35 in 400 ft")              → EyeSight moves its setpoint)
                                   │
                                   ▼
                          EyeSight does the braking
```

## 6. Difficulty read — building the UI

The honest version:

- **Custom on-screen HUD widget from scratch:** *moderate–hard right now*, because openpilot's UI is mid-migration Qt/C++ → raylib/Python. Building a bespoke widget means building on a moving target.
- **Advisory via the existing alert/event system:** *easy–moderate*, and it's the right MVP — confirmed correct in practice. Emit an event with the computed target speed + distance; the alert text + chime already render on whatever UI stack is live. Pure Python in the controls/planner layer, no C++, no rendering code. Phase 1 shipped with **zero new widget files** — the whole implementation was event/text wiring into infrastructure already composed on-screen.

Net: the *speed-target math* was largely done already (MTSC/VTSC exist and run regardless of long control). The real Phase-1 work ended up being: plumbing their output to an advisory, working around a product-level settings gate that assumed every car either has long control or ICBM, and tuning trigger thresholds (min speed, once-per-curve debounce). All tractable. The hard, risky novelty is still all in Phase 2/3.

## 11. 🟡 Incident (opened 2026-07-21, fix deployed 2026-07-21, pending real-drive confirmation)

**Symptom:** On the first real validation drive of `phase1-curve-advisory` (commit `fa6604a`), cruise control was completely unavailable from the start of the drive — repeated attempts to engage both openpilot-assisted cruise and stock/"natural" cruise threw the same persistent error. **Leading hypothesis (strong circumstantial evidence, not yet confirmed via live traceback):** stale generated capnp C++ bindings. `cereal/custom.capnp` is the schema *source*, but openpilot also ships pre-generated bindings compiled from it (`cereal/gen/cpp/custom.capnp.h` / `.c++`), which require an explicit `scons` build to regenerate — a plain `git pull`/`git checkout` + reboot does **not** rebuild them. Checked both generated files in the local dev clone directly: neither contains the `distance` field or `curveSpeedAdvisory` enum value added on this branch — they're stale relative to the schema source, and nothing (locally or, going by symptoms, possibly on-device) ever regenerated them. `longitudinal_planner.py` unconditionally writes `sccMap.distance = ...` on every single publish call, starting from the first frame — if the compiled schema plannerd actually runs against lacks that field, this throws immediately, matching "immediately... not running" exactly, and a crash-looping `plannerd` plausibly explains losing cruise access entirely (it feeds the core control state machine, not just the advisory).

**Not yet confirmed:** whether comma's manager auto-runs an incremental `scons` build on every boot (if it does, the above theory needs revisiting — the crash could be something else, or the auto-build could itself be failing silently and that failure is the real thing to chase).

**Real process gap this exposed:** earlier "you're clear to test" verification only checked that `SmartCruiseControlMap`/`CurveSpeedAdvisory` params persisted in the params store — never checked that `plannerd` was actually alive and publishing without crashing. Params persisting says nothing about process health. **Do not repeat this gap** — any future redeploy must confirm the actual process is running clean (e.g. `pgrep -af plannerd`, check for crash-loop in logs, tail `plannerd`'s recent log output) before calling it safe to drive on, not just that a param file has the right value in it.

**Deeper structural finding:** this device's branch (`phase1-curve-advisory`, forked from `release-mici`) is a true **prebuilt-only release export** — confirmed no `SConstruct` exists anywhere in the tree, on this branch or on `release-mici` itself, and (checked directly against sunnypilot's GitHub) on *any* mici-targeting branch they ship. **2026-07-26, evening — Phase 3 status-dots feature caused a real, repeated commIssue/TAKE CONTROL failure on a 3-hour highway drive; fully reverted same night, then root-caused across two investigation passes to a documented confidence level. This is a separate, more serious incident from the same-day Q12 ADSP issue above — different evidence, different (partially still-open) conclusion, do not conflate the two.**

Driving on commit `029d876b84` (the already-crash-fixed version of the status-dots/alert feature from earlier that day), ~3 hours into a continuous highway drive at ~70mph, the driver hit a real "TAKE CONTROL IMMEDIATELY" disengage — not the car's own steering (stock/mechanical, independent of openpilot), but a real, repeated loss of driver-assist control needing active intervention. Pulled over, power-cycled, worked ~4 minutes, then a second episode followed by a ~36-second burst of roughly 30 repeated disengage events. Given the severity, the two Phase 3 UI commits were reverted immediately via `git revert` (not `reset` — preserves history), before any investigation: commits `e17e87a`/`539367e`, new HEAD `539367ee6b` on `phase3-actuation`, pushed, pulled onto the device, rebooted, and reboot-verified clean — matching this project's standing discipline of reverting immediately when a live test degrades and investigating after, not debugging live in a moving car. Incident rlogs (26 segments, rlog-only, no video) were pulled from the device for offline analysis before the revert reboot could touch them.

**First investigation pass (3 parallel research threads — code review, timeline reconstruction, process-health/timing) found strong circumstantial evidence but real ambiguity.** The code-review pass found a real structural candidate: `write_ui_status()` (writes `/data/phase3_ui_status.json`, added by this feature) runs inside `plannerd`'s real-time control loop before `publish()`, and `selfdrived` has an exact watchdog (`commIssue`) that fires when a subscribed service goes stale — a plausible match. The timeline pass (via `cloudlog` inference at this stage, not yet direct message reads) found `longitudinalPlan`/`longitudinalPlanSP` — exactly what `plannerd` publishes, exactly where the new write sits — invalid in every commIssue episode. But the process-health pass found no cumulative CPU/memory/thermal buildup over the 2-hour drive (all flat), and the one publish-timing gap found near the first disengage was only 116ms — small enough to leave real doubt against an assumed (and, as the second pass found, incorrect) 500ms failure threshold. Verdict at this point: "strong circumstantial evidence, not proven."

**User was unsatisfied with that hedge and asked for a much deeper pass, explicitly requesting a confidence score, and supplied the key missing piece: a natural-experiment control dataset.** After the revert, substantially more driving happened (9 separate sessions, ~5.5 hours total, including one continuous 3-hour drive) on the reverted code with zero reported issues. Since the comma device was offline at the time, this data was pulled not from the device but directly from the home NUC's existing local rsync mirror of route data (already continuously syncing independent of device reachability — same mechanism used for Phase 2's original archive mining) — 330 rlog segments, no video, no comma SSH needed at all. Community research was also done into how other custom-fork developers add UI/status features without hitting this failure mode.

**Second investigation pass substantially changed the picture — tightened the correlation, but also disproved the originally-proposed mechanism.**
- **Exact, direct message-level correlation, not inference this time.** Reading the real `valid` flag off all 29,764 `longitudinalPlan`/`longitudinalPlanSP` messages in the incident data: invalid events cluster into exactly 7 tight windows. 6 of 7 match the real commIssue/TAKE CONTROL timestamps exactly; the 7th is an unrelated parking/reverse-gear transition, checked and correctly excluded. Zero invalid events anywhere else in the dataset.
- **The real commIssue threshold, from source** (`selfdrive/selfdrived/selfdrived.py:395-401`): alive threshold is 10x each service's own frequency — **100ms** for `carState`/`controlsState` (100Hz), not the 500ms assumed in the first pass.
- **The originally-proposed mechanism does not check out numerically.** No publish-timing gap anywhere near 100ms during any real failure in either dataset — median gap 50ms, p99 ~65ms, max ~200-235ms, **zero gaps over 500ms in either dataset, including during the three real incident episodes**. `carState`/`controlsState`'s own `valid`/`canValid`/`canTimeout` stayed clean through every episode. A from-scratch `FrequencyTracker` replication (same window sizes, same 0.8-1.2 band) showed `freq_ok=True` at all 446 invalid moments. And there's a structural/logical problem with the simple story: a cycle's freshness check is cached before that same cycle's file write runs, so the write can't retroactively invalidate its own cycle's check — it could plausibly affect the *next* cycle's margin instead, but nothing in the data confirms that either.
- **Clean A/B outcome comparison, confound explicitly checked.** Zero real commIssue events across all 5.5 hours of reverted-code driving (including the 3-hour continuous session, directly comparable in length to the incident's own pre-failure stretch) vs. three confirmed episodes in ~3 hours on the Phase3 commit — both commits confirmed directly from `initData.gitCommit` in the log data itself, not assumed from deploy timing. `freeSpacePercent` (~10% throughout, flagged as a possible confound in the first pass) is nearly identical between the two datasets — a constant baseline condition of the device, not something that varies with which code ran, so it can't by itself explain why only one dataset failed.
- **Architectural finding.** Every other live UI element in this codebase — `driver_state.py`, `confidence_ball.py`, `hud_renderer.py`, every sunnypilot addition included — reads control-loop state exclusively through real cereal/capnp pub-sub, zero exceptions found. `phase3_dots.py`'s raw-file poll and `write_ui_status()`'s raw-file write were the only per-frame file I/O anywhere in the UI layer and the only continuous write inside `plannerd`'s control loop anywhere in the entire codebase — not a style choice, unprecedented in this specific tree.
- **Community corroboration, real but non-specific.** No exact match for "custom status file → commIssue" in the local comma.ai Discord archive, but real precedent of "commIssue/TAKE CONTROL while driving, fixed by a reboot" as a known recurring consequence of custom-fork modifications generally (different fork, different cause, same symptom shape) — supports the general category, doesn't pin the specific mechanism.
- **One narrower, independent corroboration**: the earlier-noted "override detected" fallback (the new one-shot alert's first read of the status file got the wrong reason, the correct one arrived 30ms later) is a race condition in a *different* process (`selfdrived`) touching the *same* file at nearly the same real-world moment — standalone evidence of some I/O irregularity around that file right at these windows, from unrelated code.

**Final verdict, with explicit confidence scores: ~90% confidence the Phase 3 code caused these incidents** (three largely independent lines of evidence — exact message-level correlation, a clean 0-vs-3 outcome split with the free-space confound explicitly ruled out, and the architectural fact that this pattern is unprecedented anywhere else in the codebase). **~30-35% confidence in the specific originally-proposed mechanism** (blocking write → stale inputs → invalid flag) — the detailed timing numbers actively contradict the simple version of that story, and the real mechanism, if this code is genuinely the cause, must be something more subtle than a single measurable stall (affecting the next cycle's margin rather than the same one, an OS-level scheduling interaction invisible to message-level timestamps, or a subtlety in `commIssue`/`commIssueAvgFreq`'s exact trigger logic) — not resolvable from log analysis alone; would need real on-device timing instrumentation or a deliberate repro to close further. **Practical conclusion: don't re-attempt this feature with just a lower write frequency** — the real mechanism was never pinned down. Any future version needs real cereal/capnp pub-sub, matching this codebase's own universal convention, not raw file I/O from inside a control loop.
